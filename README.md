# Grain Tracker v9

Grain-trucking scale software for a country elevator: truck scale capture,
multi-load weight sheets, bin inventory, people/lots, daily reports, and a
main-office portal that receives end-of-day syncs.

## Layout

- `app/` — the scale-house application (React 19 + TypeScript + Vite +
  Tailwind + shadcn/ui frontend; Hono + tRPC + Drizzle backend on MySQL,
  with a dev-only embedded SQLite fallback). See `app/README.md`.
- `office/` — the main-office portal variant (same stack): receives EOD
  uploads from each scale house over HTTP (`x-gt-sync-key`) and shows
  per-site bin levels and upload history. See `office/README.md`.
- `gtv8-vps-setup.sh` — one-shot Ubuntu VPS setup (clones GTv9, generates
  secrets, builds `app/` with Docker Compose + MySQL behind Caddy). **This is
  the canonical install script.**
- `vps-grain-stack-setup.sh` — legacy stub; points at `gtv8-vps-setup.sh`.
- `grain-track-ubuntu-bootstrap/` — Ubuntu workstation bootstrap kit
  (checksums in `SHA256SUMS.txt`).
- `design/`, `gt-rebuild/` — design notes and rebuild recon (partly stale;
  treat code as the source of truth).
- `Grain-Tracker-Install-Guide.md` + `.docx` — operator install guide.
- `scale-dashboard-rebuild-spec.md` — a proposed single-screen scale
  dashboard rebuild. **Not implemented in this tree** — see below.

## Status of the dashboard rebuild spec

`scale-dashboard-rebuild-spec.md` (single-screen console with keyboard
shortcuts Space/Enter/N, sound beeps, ticket printing/auto-print, tare
memory, tare-deviation + duplicate-truck warnings, est-net, auto-advance,
ops overview) is **a design document only**. None of it exists in this
codebase — earlier READMEs claimed otherwise; that was wrong. What ships is
a multi-page app (Dashboard → `/scale/:sheetId` weigh console → Sheets
archive). Spec-aligned groundwork that IS present but unwired:

- `sheets.truckTares` API (tare memory query; no UI calls it)
- `#ticket-print` print stylesheet in `app/src/index.css` (no component
  renders it)

## Configuration (environment)

| Variable | Meaning |
| --- | --- |
| `DATABASE_URL` | MySQL connection string (production) |
| `ADMIN_PASSWORD` | password for admin-gated changes: site admin, **editing an existing farmer**, bin create/edit/adjust, **changing or voiding loads on a CLOSED ticket**, and sync settings. Adding farmers/lots/sheets, weighing, and closing lots need no password. **Currently OPTIONAL (owner request, "for now"): when unset or left at the default `grain-admin`, the admin gate is OPEN — gated changes need no password, and the server logs a loud boot warning. Set any non-default value to re-enable the gate.** |
| `SYNC_KEY` | **Office portal only.** Shared secret the sync receiver checks the `x-gt-sync-key` header against (timing-safe). **Fail-closed: if unset/empty the office refuses ALL sync requests with 503, in every environment.** The scale house stores the same value in Settings → Main-office sync (the `officeKey` setting). Generated by `gtv8-vps-setup.sh`. |
| `SEED_DEMO` | demo dataset on first boot of an *empty* database. Defaults to on in dev, **off in production** (`SEED_DEMO=true` to opt in). |
| `ALLOW_OFFLINE` | `1` to permit the embedded SQLite fallback in production. Without it, production refuses to boot when MySQL is unreachable. |
| `TZ` | day boundaries for the daily report / EOD close follow this zone. Keep the app and MySQL containers on the same zone. |

## Development

```bash
cd app
npm ci
npm run dev        # Vite dev server (falls back to embedded SQLite w/o MySQL)
npm run check      # typecheck
npm run test       # vitest (bushels/shrink + lot-code units)
npm run build      # vite build + esbuild server bundle
npm start          # production server on :3000
npm run smoke      # end-to-end tRPC smoke test against a running server
                   # (mutates data — refuses unless the DB looks throwaway,
                   #  i.e. /api/health reports offline mode; --i-know overrides)
```

`office/` uses the same commands.

## Offline database backups (P1-14)

When the app runs on the embedded SQLite database (no MySQL), that file is
the only copy of the data, so it is backed up automatically and on demand:

- **Automatic** — while the app server runs in offline mode it copies the
  database once a day to `data/backups/`, keeping the newest 7
  (`startDailyBackup`, wired in `app/api/boot.ts`).
- **Manual** — `npm run backup` from the repo root takes a copy immediately
  (same location, same retention). Honors `GT_OFFLINE_DB_PATH`.

Copies use SQLite's online backup API, so they are consistent even while the
scale is weighing.

**Restore drill** (practice this before you need it):

1. Stop the app server.
2. Confirm the live file: `data/grain-tracker-offline.db` (or the path in
   `GT_OFFLINE_DB_PATH`).
3. Pick a backup from `data/backups/` — filenames carry the timestamp:
   `grain-tracker-offline-YYYYMMDD-HHMMSS.db`.
4. Copy it over the live file, e.g.
   `cp data/backups/grain-tracker-offline-20251001-020000.db data/grain-tracker-offline.db`
   (delete any leftover `-wal`/`-shm` sidecar files from the crashed state
   first — the backup is self-contained).
5. Restart the app and spot-check the archive: recent tickets and bin levels
   should match the backup's timestamp.

Restoring loses everything entered after the backup was taken — that is the
point of the daily cadence; take a manual `npm run backup` before risky
maintenance.
